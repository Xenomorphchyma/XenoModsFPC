# XenoModsFPC Plugin SDK (API 2)

XenoModsFPC - сборка FPC-версии Space Rangers HD со встроенным хостом
плагинов. Он загружает нативные части модов так же, как XenoNativeLoader
делает это для обычной (Delphi) игры, но без патчей машинного кода:

| XenoNativeLoader (Delphi) | XenoModsFPC |
| --- | --- |
| `XenoPlugin_Query` / `XenoPlugin_Initialize` | `XenoFpcPlugin_Query` / `XenoFpcPlugin_Initialize` (+ необязательный `XenoFpcPlugin_Shutdown`) |
| сигнатуры, трамплины, `VirtualProtect` | хук по имени: `host->hook("TShip.GetName", ...)` |
| вызов функции игры по адресу | `host->invoke(info, self, args, &result)` |
| смещения полей (`ship + 0x461`) | `host->fieldInfo("TShip", "ChameleonActive", &info)` |
| экспорт DLL для `ImportedFunction` | `host->registerScriptFunction(...)` |
| `host->configGetInt` и т. п. | то же, строки UTF-8 |
| `XenoNative.log` | `rangers-fpc.log`, подсистема `xeno` |

Заголовок: `xeno_fpc_plugin_api.h`. Пример: `example/XenoFpcExample.cpp`.
Список всех методов, которые можно перехватить: `XenoHooks.txt`.

## Где лежит плагин

Как и у лоадера:

```text
Mods\<Категория>\<Мод>\
  ModuleInfo.txt
  Native\
    <Мод>.XenoPlugin.dll        (Windows; .XenoPlugin.so на Linux/Android)
    <Мод>.XenoPlugin.ini        (необязательно; [Plugin] Enabled=0 отключает)
```

Плагин загружается, только когда мод включён в менеджере модов, и
выгружается, когда его выключают. Перезапуск игры не нужен. DLL без
`XenoFpcPlugin_Initialize` (например, плагин только для XenoNativeLoader)
пропускается с предупреждением в логе, игра не падает.

**Одна DLL для обеих версий игры.** Если экспортировать и `XenoPlugin_*`, и
`XenoFpcPlugin_*`, одна и та же DLL работает и с XenoNativeLoader, и с
XenoModsFPC. Общую логику мода оставьте общей, разными будут только
"точки входа": сигнатуры для Delphi-версии и хуки по имени для FPC.

## Хуки методов

Перехватить можно любую подпрограмму игры, у которой есть тело: метод,
конструктор, деструктор или функцию модуля, всего около 8700. Для этого не
нужно ни менять EXE, ни писать автору XenoModsFPC: при сборке игры каждая
подпрограмма получает точку входа для хуков.

```cpp
// После TRanger.GetName: дописать звание к имени рейнджера.
void XENO_FPC_CALL AfterGetName(void* user, XenoFpcCall* call) {
    char name[256];
    host->valueGetString(call->result, "WideString", name, sizeof(name));
    std::string text = std::string("Капитан ") + name;
    host->valueSetString(call->result, "WideString", text.c_str());
}

host->hook("TRanger.GetName", XENO_FPC_HOOK_AFTER, 0, 0, AfterGetName, nullptr);
```

### Имена

- метод: `TShip.GetName` или с модулем `aShip.TShip.GetName`;
- функция модуля: `EC_Str.TrimWideString`;
- перегрузки различаются типами параметров:
  `TFoo.Bar(Integer, WideString)`. Без типов `hook` откажется и напишет в лог
  все варианты.

Полный список с параметрами и типами - `XenoHooks.txt`. Во время игры его
можно перебрать через `hookCount()`/`hookInfoAt()`, а одно имя найти через
`hookFind()`.

### Обработчики

Обработчик получает `XenoFpcCall`:

- `self` - объект (для методов класса - сам класс, для функций модуля -
  `NULL`);
- `arguments[i]` - указатель на i-й аргумент, для `var`/`out` - на
  переменную вызывающего кода. Описание аргументов (имя, тип, размер) - в
  `call->info->arguments`;
- `result` - указатель на результат функции, для процедур `NULL`.

`XENO_FPC_HOOK_BEFORE` вызывается до оригинала. Он может:

- поменять аргументы, кроме `const`;
- заменить метод целиком: записать результат и поставить
  `call->skipOriginal = 1`. Оригинал тогда не выполняется.

`XENO_FPC_HOOK_AFTER` вызывается после оригинала (или после замены) и может
поменять результат. `call->originalRan` показывает, выполнялся ли оригинал.
Если оригинал выбросил исключение, обработчики `after` не вызываются.

Строки (`WideString`, `AnsiString` и др.) нельзя менять через `memcpy`: для
них есть `valueGetString`/`valueSetString` по имени типа. Они работают и с
аргументами, и с результатом, и с полями объектов.

### Переопределения

`XENO_FPC_HOOK_OVERRIDES` ставит хук на метод и на все его переопределения в
классах-потомках. Базовый метод может быть абстрактным:
`TShip.GetName` с этим флагом сработает для рейнджеров, пиратов, доминаторов
и остальных кораблей. Если переопределение вызывает `inherited`, обработчик
всё равно получит один вызов на объект.

Без флага хук стоит только на одной реализации: `TShip.Foo` не сработает,
если `TRanger` переопределил `Foo` и не вызывает `inherited`.

### Несколько модов на одном методе

Моды не обязаны знать друг о друге:

- обработчики `before` идут по приоритету (меньше - раньше), при равном
  приоритете - в порядке модов в менеджере. Каждый видит аргументы такими,
  какими их оставил предыдущий;
- обработчики `after` идут в обратном порядке, так что каждый мод
  "оборачивает" следующие за ним;
- заменить метод может только один мод - первый. Следующие видят
  `call->replacedBy` (id плагина-заменителя) и не должны трогать результат;
  если они тоже попросят замену, хост откажет и напишет об этом в лог;
- если результат одного вызова меняли несколько модов, хост один раз
  отметит это в логе.

Меняйте значения относительно текущих ("умножить цену на 1.1"), а не
задавайте с нуля: тогда моды на одном методе складываются, а не спорят.

Хуки плагина снимаются сами, когда его мод выключают. Снять раньше -
`hookRemove(handle)`.

### Вызов функций игры

`invoke` вызывает любую подпрограмму из списка с флагом
`XENO_FPC_ROUTINE_INVOKABLE` (почти все), вместе с хуками других модов:

```cpp
const XenoFpcHookInfo* info = nullptr;
host->hookFind("EC_Str.CountDelimitedPartsW", &info, 1);
void* text = nullptr;     // место под WideString
void* delims = nullptr;
host->valueSetString(&text, "WideString", "a;b;c");
host->valueSetString(&delims, "WideString", ";");
void* args[] = {&text, &delims};
int32_t count = 0;
host->invoke(info, nullptr, args, &count);        // count == 3
host->valueSetString(&text, "WideString", nullptr);   // освободить строки
host->valueSetString(&delims, "WideString", nullptr);
```

Для методов передайте объект в `self`. Место под строковый результат
обнулите заранее и освободите так же через `valueSetString(..., nullptr)`.

### Потоки и скорость

Хук вызывается в том потоке, где вызван метод: ход галактики считается в
рабочем потоке, поэтому обработчики должны быть потокобезопасными, если
трогают общие данные.

Пока на подпрограмму не поставлен хук, она стоит почти столько же, сколько в
обычной сборке. Вызов с хуком дороже на десятки наносекунд, поэтому для
методов, которые зовутся миллионы раз за ход (математика, доступ к спискам),
лучше найти место повыше.

Не перехватываются: `inline`- и `external`-подпрограммы, вложенные
подпрограммы, заголовки с условной компиляцией внутри и несколько самых
частых мелких функций, перечисленных в `xenomods/hooks_exclude.txt`. Их нет в
`XenoHooks.txt`.

## Как перенести мод с XenoNativeLoader

1. Отделите логику мода от слоя хуков (как `price_math.cpp`,
   `generator_plan.cpp` у XenoMods). Она переносится без изменений.
2. Каждый патч замените хуком на тот же метод игры по имени. Для частых
   случаев есть и готовые события (ниже).
3. Каждое смещение поля запросите через `fieldInfo` один раз в
   `Initialize` и кешируйте. Унаследованные поля находятся и по классу
   потомка (`TRanger` -> поля `TShip`). Таблица генерируется из исходников
   при сборке EXE, поэтому плагин не ломается при обновлении игры.
4. Скриптовые функции регистрируйте с той же сигнатурой, что в блоке
   `ScriptLibs` CFG мода. Имя библиотеки - имя файла из `Path` без `.dll`.
   CFG и скрипты мода менять не нужно.
5. Объекты из скриптов (`dword`) - указатели на объекты игры. Перед
   использованием проверяйте `isLiveObject` и `isInstanceOf`.

## События

Готовые точки, которые удобнее хука на конкретный метод:

| Событие | Когда | Что можно изменить |
| --- | --- | --- |
| `Frame` | каждый проход главного цикла | - |
| `Galaxy.Created` | создание `TGalaxy` (новая игра и загрузка) | `sectorCount` |
| `Galaxy.PlanStar` | выбор сектора звезды при генерации | `sector` |
| `Galaxy.LayoutDone` | после каждой попытки раскладки секторов | `done` |
| `Galaxy.ContourNoEar` | обрезка скрытого сектора зашла в тупик | `removeVertex` |
| `Galaxy.StationSpawning` | этап 8 нового дня | `run` |
| `Item.Created`, `Item.Destroyed`, `Item.Loaded` | жизненный цикл `TItem` (могут прийти из потока хода) | - |
| `Item.SaveCost` | `TItem.SaveToBuffer` пишет цену | `cost` |
| `Kling.Camouflage` | доминатор проверяет камуфляж не игрока | `handled`, `effective` |
| `Hangar.Opened`, `Hangar.Closed` | экран ангара | - |
| `Hangar.Refresh` | заполнение мест 1..8 (каждый кадр) | `handled` |
| `Hangar.Key` | клавиша в ангаре | `handled` |
| `Music.PlayCategory` | смена музыки места | `skip` |
| `Music.StopImmediately`, `Music.PlaceFade` | остановка и затухание музыки | `keep` |
| `Sound.VolumeRamp` | плавное изменение громкости (поток звука) | `step` |

Подписчики вызываются по порядку: сначала встроенные моды XenoModsFPC, потом
плагины в порядке модов. Исключение в обработчике (события или хука)
записывается в лог и не роняет игру.

## Сборка

Windows, 32-битная игра (как Steam-версия):

```bash
i686-w64-mingw32-clang++ -std=c++17 -O2 -shared -static -o MyMod.XenoPlugin.dll MyMod.cpp
```

Подойдёт и MSVC (`cl /LD`, x86): все функции API - `cdecl`. Для 64-битной
сборки игры нужна x86_64-DLL, для Linux/Android - `.so` под нужную
архитектуру (`-fPIC -shared`, Android NDK для arm64).

## Проверка

`Rangers.exe --xeno-selftest` после загрузки главного меню прогоняет тесты
встроенных модов и хоста (включая хуки), генерирует новую игру с выбранными
модами, выполняет ходы, сохранение и загрузку и выходит с кодом 0 или 1.
Окно при этом скрыто, звука нет (`--xeno-visible` - с окном и звуком).
Отчёт - `xeno_selftest.txt` в папке пользователя. Если включён мод с примером
плагина, проверяются и его загрузка, скриптовая функция и хук на
`TGalaxy.NextDay`.
